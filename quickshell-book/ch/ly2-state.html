ly2lyne-dots 2: One File for Every Setting

In most rices, settings are scattered: colours in one file, bar options in another, a few numbers hard-coded in widgets. lyne puts every setting in a single JSON file, state.json, and gives the whole shell one way to read and change it. That decision is what makes its 27-page Settings app possible, and it's the first thing we build.

The idea#

{
  "theme": { "name": "nord" },
  "bar": { "style": "floating", "workspaces": { "style": "dots" } }
}

A widget never opens this file. It asks the state service for a key path:

StateService.get("bar.style", "docked")        // "floating"
StateService.get("bar.height", 33)             // not in the file → from defaults.json, else 33
StateService.set("bar.workspaces.style", "numbers")

Three rules make it work:

  1. Only keys you changed are in state.json. Everything else comes from defaults.json, which ships with the shell. A fresh install has no state.json at all.
  2. get() is reactive. A binding that calls get("bar.style") re-evaluates when that value changes, whether it was changed by the Settings app, by qs ipc call state set …, or by you editing the file in a text editor.
  3. set() saves by itself, a moment later, in one write.

These are the values the shell uses until you change them. The groups mirror lyne's own defaults.json (in the original it's .data/quickshell/defaults.json, with about 40 groups): theme, opacity, geometry (corner radii, spacing, padding), typography, animations (three durations in milliseconds), bar, launcher, notifications, osd, idle, power, wallpaper and screenshot.

When lyne-dots updates, lyne update adds new keys to defaults.json, and you get them without your state.json being touched. That's the benefit of storing only what you changed.

The state service, line by line#

lyne/services/StateService.qmlpragma Singleton
import QtQuick
import Quickshell
import qs.services
import Quickshell.Io

// Every setting of the shell lives in ONE file, ~/.config/lyne/state.json.
// Widgets never read the file: they ask for a key path like "bar.style",
// and get the value from state.json, or from defaults.json when it isn't set.
Singleton {
    id: root

    readonly property string statePath: Quickshell.env("HOME") + "/.config/lyne/state.json"
    readonly property string defaultsPath: Quickshell.shellPath("defaults.json")

    property var state: ({})              // what's in state.json
    property var defaults: ({})           // what's in defaults.json
    property bool isLoading: true         // true until state.json has been read once

    // --- Telling bindings that something changed ---------------------------
    // `state` is a plain JavaScript object changed in place, which QML can't
    // see. So every top-level key ("bar", "theme"…) gets a small counter
    // object. get("bar.style") reads the "bar" counter, which makes the
    // binding depend on it; set("bar.style", …) bumps the counter, and only
    // bindings that read something under "bar" re-evaluate.
    property var _counters: ({})
    property int revision: 0              // bumped when defaults.json (re)loads

    Component {
        id: counterComponent
        QtObject { property int rev: 0 }
    }

    function _depend(path) {
        const top = path.split(".")[0];
        let counter = _counters[top];
        if (!counter) {
            counter = counterComponent.createObject(root);
            _counters[top] = counter;
        }
        return counter.rev;               // reading it is what creates the dependency
    }
    function _bump(top) {
        if (_counters[top])
            _counters[top].rev++;
    }

    // --- Reading and writing with dot paths -------------------------------
    function _lookup(obj, path) {
        let current = obj;
        for (const key of path.split(".")) {
            if (current !== null && typeof current === "object" && key in current)
                current = current[key];
            else
                return undefined;
        }
        return current;
    }

    function _assign(obj, path, value) {
        const keys = path.split(".");
        let current = obj;
        for (let i = 0; i < keys.length - 1; i++) {
            if (typeof current[keys[i]] !== "object" || current[keys[i]] === null)
                current[keys[i]] = {};
            current = current[keys[i]];
        }
        current[keys[keys.length - 1]] = value;
    }

    // state.json first, then defaults.json, then the fallback written in the code
    function get(path, fallback) {
        root.revision;
        _depend(path);
        const value = _lookup(state, path);
        if (value !== undefined)
            return value;
        const def = _lookup(defaults, path);
        return def === undefined ? fallback : def;
    }

    function isDefault(path) {
        root.revision;
        _depend(path);
        const value = _lookup(state, path);
        return value === undefined || JSON.stringify(value) === JSON.stringify(_lookup(defaults, path));
    }

    function set(path, value) {
        if (JSON.stringify(_lookup(state, path)) === JSON.stringify(value))
            return;                       // nothing changes: no write, no re-evaluation
        _assign(state, path, value);
        _bump(path.split(".")[0]);
        if (!isLoading)
            saveTimer.restart();
    }

    function reset(path) {
        const def = _lookup(defaults, path);
        if (def !== undefined)
            set(path, JSON.parse(JSON.stringify(def)));
    }

    // --- The files ------------------------------------------------------------
    function _apply(text) {
        let next;
        try {
            next = JSON.parse(text);
        } catch (e) {
            console.warn("[State] state.json is not valid JSON:", e);
            isLoading = false;
            return;
        }
        // which top-level keys differ from what we have now?
        const keys = new Set([...Object.keys(state), ...Object.keys(next)]);
        const changed = [...keys].filter(k => JSON.stringify(state[k]) !== JSON.stringify(next[k]));
        state = next;
        isLoading = false;
        for (const key of changed)
            _bump(key);
    }

    // many set() calls in a row (dragging a slider) become one write
    Timer {
        id: saveTimer
        interval: 300
        onTriggered: stateFile.setText(JSON.stringify(root.state, null, 2) + "\n")
    }

    FileView {
        id: defaultsFile
        path: root.defaultsPath
        watchChanges: true
        onFileChanged: reload()
        onLoaded: {
            try {
                root.defaults = JSON.parse(text());
                root.revision++;
            } catch (e) {
                console.warn("[State] defaults.json is not valid JSON:", e);
            }
        }
    }

    FileView {
        id: stateFile
        path: root.statePath
        watchChanges: true                // edits from a text editor or a script apply live
        atomicWrites: true                // never leave a half-written file behind
        printErrors: false
        onFileChanged: reload()
        onLoaded: root._apply(text())
        onLoadFailed: {
            // first start: no state.json yet. Everything comes from defaults,
            // and the first set() creates the file.
            root.isLoading = false;
        }
    }

    IpcHandler {
        target: "state"
        function get(path: string): string { return JSON.stringify(root.get(path, null)); }
        function set(path: string, json: string): void { root.set(path, JSON.parse(json)); }
        function reset(path: string): void { root.reset(path); }
    }
}

lines 16–18The data
property var state: ({})              // what's in state.json
property var defaults: ({})           // what's in defaults.json

state and defaults are plain JavaScript objects (var). isLoading is true until state.json has been read; set() doesn't save during that time, and the idle monitors in shell.qml wait for it.

lines 20–27The reactivity problem
// --- Telling bindings that something changed ---------------------------
// `state` is a plain JavaScript object changed in place, which QML can't
// see. So every top-level key ("bar", "theme"…) gets a small counter
// object. get("bar.style") reads the "bar" counter, which makes the
// binding depend on it; set("bar.style", …) bumps the counter, and only
// bindings that read something under "bar" re-evaluate.
property var _counters: ({})
property int revision: 0              // bumped when defaults.json (re)loads

QML notices when a property is assigned. But state.bar.style = "dots" changes something inside an object: the property state itself still holds the same object, so nothing would update. The fix is a small counter per top-level key. Reading a counter inside get() makes the calling binding depend on it; changing it later makes that binding run again.

lines 29–32A counter
Component {
    id: counterComponent
    QtObject { property int rev: 0 }
}

A tiny object with one int. A Component lets us create as many as needed.

lines 34–42Depending on a key
function _depend(path) {
    const top = path.split(".")[0];
    let counter = _counters[top];
    if (!counter) {
        counter = counterComponent.createObject(root);
        _counters[top] = counter;
    }
    return counter.rev;               // reading it is what creates the dependency

For "bar.workspaces.style" the top key is "bar". The first time it's needed, a counter is created and remembered in _counters. Then its rev is read, and reading is all it takes: QML records that the current binding used rev.

lines 43–46Announcing a change
function _bump(top) {
    if (_counters[top])
        _counters[top].rev++;
}

Adding one to rev notifies every binding that read it. Only bindings that read something under that top key run again, so changing bar.style doesn't re-evaluate every theme binding in the shell.

lines 49–58Following a path

lines 82–87isDefault()

True when the key isn't in state.json, or holds the same value as the default. Settings rows use it to show a reset button only for changed values (lyne-dots 11: The Settings App). JSON.stringify compares lists and objects by content.

lines 89–96set()
function set(path, value) {
    if (JSON.stringify(_lookup(state, path)) === JSON.stringify(value))

lines 98–102reset()

Set the key back to its default. JSON.parse(JSON.stringify(…)) copies it, so later changes to the state can't change the defaults object.

In the original

The lyne state command opens the file, lyne state sync adds new default keys after an update.

Exercise 1Warm-upYour first setting

Add "clock": { "seconds": false } to defaults.json. Then, in a scratch widget, show the time with seconds only when StateService.get("clock.seconds", false) is true. Toggle it from the terminal.

Exercise 2PracticeA toggle helper

Add function toggle(path) to the service that flips a boolean setting, and an IPC function for it. Then qs -c lyne ipc call state toggle bar.autoHide should hide and show the bar.

✅ Solution
function toggle(path) { set(path, !get(path, false)); }
// in the IpcHandler:
function toggle(path: string): void { root.toggle(path); }
Exercise 3PracticeProve the reactivity trick

Remove _depend(path); from get(), restart, and change bar.style from the terminal. What happens, and why? Put it back.

🧠 Why it works

Without reading the counter, the bindings that call get() don't depend on anything that changes, so they never re-run: the file changes, but the bar keeps its old style until a restart.

Exercise 4ChallengeUndo

Keep the last 20 changes in a list ({ path, before }) inside set(), and add undo() that restores the most recent one. Expose it over IPC.
